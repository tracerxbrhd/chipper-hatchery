# CHIPPER 0.1 — план тестирования и приёмки

**Репозиторий:** tracerxbrhd/chipper-hatchery  
**Бот:** @chipperhatcherybot  
**Спецификация:** DOCS/GDD_0.1.md  
**Ответственный за реальную приёмку:** владелец проекта с несколькими своими Telegram-аккаунтами.  
**Статус:** критерии для проверки, не отчёт о выполненных тестах.

## 1. Цель и принцип приёмки

Готовность 0.1 означает, что игра действительно запускается в Telegram, сохраняет прогресс на сервере, не смешивает аккаунты, корректно переживает ошибки и повторные нажатия, а все обещанные игровые экраны функциональны. Собранный интерфейс с заглушками не является завершённой версией.

Сценарии реальных Telegram-аккаунтов нельзя засчитывать как пройденные на основании моков, unit-тестов или фиктивных скриншотов.

Обозначения: A, B, C — **три разных реальных Telegram ID**; A1/A2 — два устройства или две сессии **одного** Telegram ID A; G — локальный dev/mock-режим (не production).

## 2. Подготовка к тестированию

- [ ] В боте настроено открытие актуального Mini App по адресу из фактического вывода deploy.
- [ ] Схема базы применена штатной миграцией и совпадает с кодом.
- [ ] Подтверждён запуск Mini App в Telegram на Android и iOS (если оба устройства доступны); Desktop/Web отдельно.
- [ ] В конфигурации репозитория и истории git нет Bot API token, tgcloud CLI access token, секретов, приватных пользовательских данных.
- [ ] Известны команды локального запуска, сборки, тестов и штатного деплоя; есть инструкция для владельца.
- [ ] Для тестового аккаунта допустим сброс тестового прогресса **только вручную в контролируемом dev/staging окружении**, не глобальной операцией по продакшену. Нельзя проектировать кнопку массового сброса без контроля.

## 3. Обязательные ручные сценарии: аккаунты A/B/C

| ID | Действие | Ожидаемое поведение |
|---|---|---|
| U01 | A запускает Mini App впервые | Одно стартовое яйцо, понятный onboarding, затем один активный питомец |
| U02 | B входит впервые после A | Собственное яйцо и питомец, никакие данные A не видны |
| U03 | C входит впервые | Отдельный третий профиль, без пропущенного onboarding и дубликатов |
| U04 | A обновляет приложение, полностью закрывает и открывает снова | То же имя, ID, облик, потребности, баланс и активный питомец |
| U05 | A переименовывает птицу, меняет её состояние, затем открывает B | У B ничего не меняется; A и B не разделяют кэш профиля |
| U06 | B входит на устройстве/клиенте после A | Профиль строго B, ни мгновения чужой коллекции (очистка кэша состояния на смене auth) |
| U07 | A получает ещё одну птицу и переключает активного | В доме только выбранный питомец, остальные остаются в коллекции |
| U08 | A переключает 5–10 раз подряд | Нет дополнительных пёрышек, изменения cooldown и нарушения состояния |
| U09 | A переименовывает птицу, B пытается воздействовать на неё по её chick_id | Сервер возвращает отказ; владелец и данные птицы A не меняются |
| U10 | A получает первое яйцо, повторяет bootstrap / welcome action | Стартовый подарок не повторяется |
| U11 | A получает редкий или обычный облик | Редкость косметическая, ID стабилен, при обновлении результат не перебрасывается |
| U12 | A закрывает приложение во время сна | Сон заканчивается по серверному времени; после повторного входа бодрость восстановлена |
| U13 | A закрывает приложение во время инкубации | Яйцо остаётся, время считается на сервере; после готовности можно вылупить |
| U14 | A отсутствует длительное время (тестировать эмуляцией часов только в тестах) | Птица жива, характеристики не падают ниже 35, реальной смерти нет |
| U15 | A играет в мини-игру повторно в течение 20-часового окна | Развлекаться можно, но дополнительной валютной награды нет |
| U16 | B имеет другой баланс, другую птицу, другое время сна | Эти значения не влияют на A и C |

Примечание: для экономии реального времени долгие задержки (20 ч, 72 ч) проверяются автоматическими тестами с контролируемыми часами. В реальном Telegram достаточно выполнить начало процесса, перезаход и завершение хотя бы одного настоящего таймера; нельзя искажать продакшен-время или вручную менять баланс боевых аккаунтов ради тестов.

## 4. Конкуренция запросов и злоупотребления

| ID | Проверка | Критерий |
|---|---|---|
| C01 | A1/A2 одновременно стартуют в первый раз | Только один стартовый экземпляр и один счётчик игрока |
| C02 | 10 одновременных одинаковых вызовов выдачи награды | Ровно одно начисление |
| C03 | Двойное нажатие «Купить яйцо» | Баланс уменьшается один раз, один инкубатор занят одним яйцом |
| C04 | 10 параллельных вызовов «Вылупить» для одного яйца | Создаётся ровно один chick_id; все успешные повторы ведут к тому же результату |
| C05 | Повтор после ответа сервера, потерянного сетью | Операция завершается идемпотентно, нет новой выдачи |
| C06 | Попытка купить яйцо при балансе меньше 6 | Отказ без отрицательного баланса |
| C07 | Запрос на другого пользователя с подставным userId / ownerId | Сервер игнорирует эти поля либо отклоняет запрос; Telegram ID берётся только из verified context |
| C08 | Несуществующий/чужой chick_id для ухода, переименования, переключения | Отказ без изменения данных |
| C09 | Попытка получить награду мини-игры без server-issued attempt | Отказ |
| C10 | Завершение мини-игры до минимально допустимой длительности | Отказ |
| C11 | Глобальная награда за уход во время переключения двух птиц | Две награды не выдаются |
| C12 | Перезапуск в середине запроса / обрыв связи | Нет частично выполненного расхода без корректного результата или восстановления |
| C13 | Длительный простой активного, затем активация другого | Нет двойного списания времени; неактивный не деградирует |
| C14 | Проверка попытки вызвать endpoint вне Telegram | Отказ для production-auth; dev mock не становится production backdoor |

**Важно:** если неполная атомарность предоставляемой платформы делает C03/C04/C12 ненадёжными, это **блокер выпуска 0.1**. Не прячьте проблему за disabled-кнопкой, задержкой на клиенте или комментариями TODO.

## 5. Игровой UX и визуальная приёмка

- [ ] На экране «Дом» сразу виден оригинальный анимированный цыплёнок, а не emoji-заглушка.
- [ ] Понятны кормление, игра и сон; видна обратная связь после действий и при cooldown.
- [ ] В инкубаторе есть фазы «свободен / инкубируется / готов / вылупление».
- [ ] Коллекция отображает разные облики, уникальные карточки, выделение активного и переименование.
- [ ] Отображены три возрастных стадии одной птицы, исходные особенности узнаваемы.
- [ ] Мини-игра играбельна: начало, таймер, очки, конец раунда, корректная награда.
- [ ] Интерфейс корректен на ширине около 320, 360, 390 и 430 px; нет перекрытия нижних кнопок Telegram UI/safe area.
- [ ] Светлая/тёмная тема Telegram не ломает контраст; уменьшение анимации учтено.
- [ ] Есть состояния загрузки, пустой коллекции, отсутствия сети, истёкшего cooldown и серверной ошибки.
- [ ] Нет внешних ссылок в UI на чужой проект и нет прямого копирования графики ChickFocus.
- [ ] Обновление страницы и back/forward не повреждают игру.
- [ ] При открытии браузером вне Telegram ясно объясняется, как запустить приложение в боте, без реального доступа к чужим данным.

## 6. Автоматические проверки, обязательные до PR

- [ ] TypeScript typecheck / статическая проверка серверного JavaScript;
- [ ] линт и сборка фронтенда;
- [ ] unit-тесты чистой игровой логики (clock и random как зависимости);
- [ ] integration/contract тесты API, включая авторизацию и IDOR;
- [ ] тесты одновременных вызовов и идемпотентности;
- [ ] проверки расчёта офлайн-прогресса / сна / инкубации / взросления;
- [ ] хотя бы один UI smoke для онбординга, переключения и мини-игры (если окружение позволяет);
- [ ] отсутствие токенов и секретов в коммитах;
- [ ] зафиксированы точные команды, дата и результаты запуска.

## 7. Матрица итогов

Для каждого сценария Codex должен указать один из статусов:

- **PASS — automated**: реально выполненный автоматический тест с идентификатором и результатом.
- **PASS — live**: проверено в настоящем Telegram, дата и устройство указаны.
- **PENDING — user acceptance**: готово к пользовательской проверке с реальным Telegram-аккаунтом.
- **BLOCKED**: нет доступа, платформенный лимит/дефект, отсутствует контракт или воспроизводимая ошибка.
- **FAIL**: тест реально не прошёл, указать шаги и причину.

Не приравнивать тестовый браузерный mock к успешной проверке real Telegram authorization. Отчёт должен содержать SHA коммитов, URL PR, где размещён тестовый Mini App (если реально развёрнут), и точные действия, необходимые владельцу для принятия релиза.
