## 3. Технологический фундамент

Предпочтительный стек:
- фронтенд: React + TypeScript + Vite, мобильный интерфейс для Telegram WebView;
- графика: собственный SVG/CSS с анимациями, без тяжёлых 3D/внешних платных библиотек;
- сервер: Telegram Serverless, код в tgcloud/ в виде поддерживаемых **.js** модулей;
- база: встроенная SQLite через официальный sdk/db;
- автоматические проверки: выбранный адекватный набор (например Vitest, ESLint, typecheck, Playwright при наличии окружения);
- локальная разработка: отдельный **явно обозначенный dev-mock adapter**, который никогда не используется для production-авторизации.

Ориентируйся на актуальные источники:
- https://blogfork.telegram.org/bots/serverless
- https://core.telegram.org/bots/webapps

**Платформенная дисциплина:**
- Используй npx tgcloud init для существующего фронтенд-проекта в корректном месте; не уничтожай существующие файлы.
- Сгенерированная CLI документация docs/tgcloud-sdk.md должна стать источником сигнатур SDK.
- В tgcloud/ — именно runtime-доступные модули: endpoints/, handlers/, lib/, schema.js. В endpoints/ и handlers/ файлы располагаются без вложенных подпапок; внутренние модули импортируются с расширением .js.
- Не импортируй npm-пакеты или Node API внутри V8-Serverless-runtime, не полагайся там на fs/process/Buffer.
- Не путай npx tgcloud push (код/статические файлы) и npx tgcloud migrate (схема БД).
- Встроенная база не даёт внешних ключей. Целостность и ownership — на уровне приложения.
- Проверенный Telegram ID получай из ctx.initData.user.id на сервере. Никогда не доверяй userId, присланному клиентом.
- Для клиента используй подтверждённый метод Telegram.WebApp.Serverless.call и официальные Telegram WebApp API (готовность, viewport, theme, back button, safe area при наличии).
- Производственный backend не должен давать данные при отсутствии валидного Telegram initData.

**Особенно важно:** изучи реальные гарантии атомарности SQLite API данной платформы. Гонки на вылуплении/расходовании пёрышек/выдаче наград/переключении питомца не должны позволять дубликаты. Рассмотри single-statement compare-and-swap (revision), уникальные ограничения, идемпотентные operation receipts или другой проверенный механизм. Не изображай многозапросную транзакцию, если API её не предоставляет. Поведение должно быть проверено тестами одновременных вызовов. Если критический инвариант невозможно обеспечить на платформе — честно обозначь блокер и безопасный путь решения, а не скрывай его.

## 4. Реализуемый функционал — без пропусков

### 4.1 Новый пользователь
- Автоматическое создание одного профиля по verified Telegram ID.
- Стартовое яйцо строго один раз.
- Интерактивное мгновенное первое вылупление (щелчки/трещинки/выход цыплёнка).
- Выбор или пропуск имени, открытие домашнего экрана.
- При refresh и двух одновременных входах стартовая птица/яйцо не дублируются.

### 4.2 Дом и уход
- Один активный питомец с живой визуальной обратной связью (idle, blink, happy, feed, play, sleepy, sleep).
- Сытость (нач. 65, −1.2/ч, корм +30), настроение (60, −0.9/ч, игра +22), бодрость (70, −1.1/ч, сон до 100).
- Падение характеристик останавливается на 35, увеличение ограничено 100.
- Кормление/игра не чаще одного эффективного раза за 4 часа на питомца.
- Сон — 45 минут серверного времени; повторный start не сбрасывает таймер.
- Во время сна другие действия ухода недоступны, но активного питомца можно переключить.
- На отдыхе в коллекции характеристики не уменьшаются; уже запущенный сон может завершиться.
- Никакой смерти/воскрешения.

### 4.3 Взросление и облики
- Птенец сразу, подросток после ≥20ч и ≥1 цикла заботы, взрослый после ≥72ч и ≥3 циклов заботы с ≥20ч между ними.
- 12 **собственных** согласованных обликов: 6 обычных (категория 70%), 4 необычных (25%), 2 редких (5%). Внутри категории равновероятно.
- Сервер выбирает результат один раз и хранит за неизменяемым appearance_id; перезагрузка не перебрасывает шанс.
- Качественно реализуй различимые 12 вариантов, а не 12 названий над одинаковым SVG; для трёх стадий сохраняй узнаваемые особенности.
- Редкость косметическая.

### 4.4 Коллекция
- Чёткий список всех собственных птиц, карточка с ID, датой рождения, именем, возрастом, обликом, редкостью.
- Переименование, визуальное выделение активного, мгновенное переключение.
- Каждому игроку принадлежит собственная коллекция; любая серверная операция проверяет владельца chick_id.
- Переключение не выдаёт новых бонусов и не сбрасывает cooldown.

### 4.5 Экономика, яйца, инкубатор
- Пёрышки: +1 за цикл заботы (кормление+игра одного питомца за 30 минут; глобальная выдача не чаще 20 часов), +1 за завершённую мини-игру (раз в 20 часов на игрока).
- Milestones взросления учитываются по питомцу отдельно от глобальной валютной награды.
- Обычное яйцо стоит 6 пёрышек и занимает единственный слот инкубатора; отрицательный баланс невозможен.
- Таймер обычного яйца 3 часа, отсчёт серверный и сохраняется после закрытия приложения.
- По готовности ручное вылупление, создание ровно одного chick_id. Новый цыплёнок в коллекции, текущий активный не меняется без выбора игрока.
- Не допускается двойная покупка, дубликат вылупления, обход cooldown несколькими сессиями.

### 4.6 Одна законченная мини-игра
- «Собери зёрнышки»: примерно 25 секунд, тапы по зёрнам, анимированная реакция птицы, счёт и экран результатов.
- Играть можно повторно без награды; выдача +1 пёрышко ограничена 20 часами на Telegram ID.
- Сервер выдаёт ID попытки и проверяет минимально допустимое прошедшее время, ownership, сроки и повторное использование.
- Не делать вид, что обычный browser-client может быть полностью защищён от читов; обеспечить разумный MVP антиабуз без денег.
- Мини-игра доступна и при сне питомца без изменения процесса сна.

### 4.7 Экранная система
Обязательны четыре раздела: Дом, Инкубатор, Коллекция, Активности; также onboarding, карточка питомца, настройки для звука/анимации, информативные loading/empty/error states.

Визуально: светлый почти белый фон, графитовый персонаж, умеренные цветные детали; узнаваемая оригинальная графика, мягкие закругления, маленькие и понятные подписи. Меньше «dashboard», больше живого персонажа. Никаких прямых копий ChickFocus. Главный экран должен производить впечатление готовой маленькой игры, а не админки.

Мобильные размеры, Telegram theme, back navigation, Android/iOS WebView, touch 44px+, prefers-reduced-motion, контраст, безопасные отступы, отсутствие горизонтального скролла.

## 5. Архитектура, тестируемость, защита

До имплементации договорись с агентами о доменных моделях и контракте эндпоинтов. Названия методов могут быть скорректированы, но покрытие — нет. Рекомендуемый контур: bootstrap, getHome, careAction, listChicks, activateChick, renameChick, getIncubator, buyEgg, hatchEgg, startMiniGame, finishMiniGame.

Требования:
- Все реальное состояние хранится сервером; клиент имеет только временное presentation-state.
- Серверное время — единственный источник истины. Предусмотри clock abstraction для тестов без реального ожидания 20/72 часов.
- Случайность выдачи облика — только на сервере. Предусмотри rng abstraction для повторяемых тестов.
- Никакие name, amount, ownerId, rarity, appearanceId, hatchReadyAt не считаются достоверными, если их заявляет клиент.
- Изоляция игроков по Telegram ID и проверка каждого объекта против него.
- Дедупликация и idempotency для денежных (игровых) наград, покупок, вылупления, bootstrap.
- Обработка двойного тапа, потерянного ответа сервера, повторной отправки после offline.
- Ошибки должны быть user-friendly, но не раскрывать внутренности системы.
- В production нельзя активировать mock-auth через query string, Telegram initDataUnsafe или localStorage.
- Не добавлять стороннюю аналитику, трекеры и сбор избыточных персональных данных.

## 6. Реальное тестирование: три Telegram-аккаунта

Документ DOCS/ACCEPTANCE_0.1.md обязателен, а не факультативен. Внутри альфы должны проходить ключевые сценарии:

A и B создают независимые профили и стартовых питомцев; C третий независимый пользователь. Повторный логин A восстанавливает только его коллекцию. Если открыть клиент после смены Telegram-аккаунта, нельзя показывать устаревший профиль A под B. Известный B идентификатор питомца A нельзя использовать для чужих действий. A1 и A2 (два устройства/окна одного аккаунта) не создают двойной стартовый подарок, двойные яйца или награды. Двойное hatch создаёт одну птицу и возвращает устойчивый результат. Offline-сон и инкубация завершаются по серверному времени. Неактивные птицы не деградируют. Никакая птица не погибает.

Реальную проверку с нескольких аккаунтов выполняет владелец. **Ты готовишь сборку, точный URL, инструкции и честную матрицу ожидаемых/выполненных тестов.** Не заявляй, что проверил чужие реальные аккаунты, если доступа к ним не было.

## 8. Правила самостоятельного принятия решений

- Баланс из GDD можно реализовать буквально как дефолтную конфигурацию; сделай его централизованным и тестируемым.
- Малозначимые UI-вопросы решай самостоятельно, не останавливая проект вопросами про цвет каждой кнопки.
- Не расширяй MVP системой обменов или монетизации, даже если остаётся время.
- Не ограничивайся красивым фасадом: код должен быть пригоден для продолжения разработки.
- Если техническая возможность платформы не подтверждается, сначала исследуй документы и попробуй безопасный маленький proof-of-concept, после чего выбери подтверждённый путь.
- Запрещено выдавать simulated test, screenshot из макета, dev data или неполный endpoint за production-ready результат.
- Никогда не выводи API-токены, секреты или содержимое .tgcloud/credentials в ответы, логи и коммиты.
- Любая операция, потенциально затрагивающая существующие данные бота или посторонние сервисы, требует осторожности и согласования; главное — не уничтожить данные.
- По окончании **остановись с PR, не выполняй merge**. Владелец будет вручную принимать игру на нескольких Telegram-аккаунтах.

## 9. Финальный отчёт оркестратора (по-русски)

Сдай компактный, но проверяемый отчёт:

1. HEAD/branch и URL PR.
2. Перечень реализованных подсистем.
3. Стек и подтверждённые особенности Serverless (а не предположения).
4. Доказательства сборки и тестов: команды, число пройденных/проваленных тестов.
5. Статус деплоя, URL реального Mini App (если был), состояние миграций.
6. Что именно проверить владельцу с A/B/C и A1/A2.
7. Список известных дефектов и blockers без приукрашивания.
8. Явное сообщение: **0.1 готова к приёмке / не готова**, с причиной.

**Успех — не количество созданных файлов, а работающая, цельная, приятная игра и честно проверенная серверная изоляция пользователей.**
