# Chipper 0.1 — безопасный первый деплой и приёмка

Инструкция для владельца **@chipperhatcherybot**, проверена по установленному `@tgcloud/cli 0.2.0`, его `--help` и [SDK](tgcloud-sdk.md). На момент подготовки инструкция не подтверждает живой деплой: CLI не связан с ботом, адрес приложения ещё неизвестен. Используйте только HTTPS-адрес из фактического успешного вывода `push`.

## 1. Подготовка

- Работайте в копии репозитория `tracerxbrhd/chipper-hatchery`, в ветке `feature/chipper-v0.1`/ветке PR. Сначала убедитесь, что локальные изменения не будут потеряны; зафиксируйте SHA кандидата и прежний рабочий SHA/URL, если прежний релиз существовал.
- Нужен Node.js 24: автоматические тесты используют встроенный `node:sqlite`. Выполните `npm ci` из корня проекта с `package-lock.json`.
- В [@BotFather](https://t.me/BotFather) выберите именно **@chipperhatcherybot**, включите **Serverless**, откройте **CLI Access → Access token**. Это отдельный CLI-токен формата `app<id>:<secret>`, а не Bot API token. [Источник: Telegram Serverless](https://blogfork.telegram.org/bots/serverless).
- `.tgcloud/` и `.env*` исключены из Git. Не помещайте токен в исходники, `.env.example`, команды с аргументом токена, PR, скриншоты или журналы. Не открывайте и не редактируйте credential-файлы вручную; не включайте CLI `--debug` при работе с доступом.

```powershell
node --version
npm ci
git status --short
git branch --show-current
git rev-parse HEAD
npx tgcloud login
```

Введите CLI-токен только в интерактивное приглашение `login`. Проверьте, что выбран нужный бот/проект. Сохранённые credentials остаются локально под управлением CLI.

### Если Windows использует системный proxy

При `Token saved but not verified` / `Could not reach https://cloud.telegram.org` причиной может быть маршрут подключения: Node CLI может не использовать proxy из настроек Windows автоматически. В Node.js 24.5+ включите поддержку environment proxy в той же PowerShell-сессии. Порт `10808` ниже — пример работающего локального **HTTP proxy**; замените его на HTTP-порт своего уже настроенного proxy, а не на SOCKS-порт. [Официальная документация Node.js 24](https://nodejs.org/docs/latest-v24.x/api/http.html#built-in-proxy-support).

```powershell
$env:HTTP_PROXY = "http://127.0.0.1:10808"
$env:HTTPS_PROXY = "http://127.0.0.1:10808"
$env:NODE_USE_ENV_PROXY = "1"
npx tgcloud fetch
npx tgcloud --no-pager status
```

Эти значения действуют в текущем терминале и его дочерних процессах. После сообщения о сохранённом непроверенном токене новый `login` не нужен только ради восстановления связи: `fetch` использует сохранённый токен. Повторный login нужен при отдельном отказе авторизации, например 401/403. Если используется `NO_PROXY`, убедитесь, что он не исключает `cloud.telegram.org` из нужного маршрута. После успешного `fetch` продолжите проверку `diff` из следующего раздела.

Оставьте официальный API-host `https://cloud.telegram.org`: не задавайте `TG_CLOUD_API_URL` на чужой домен, которому CLI отправит токен. Не отключайте проверку TLS и не сохраняйте proxy-настройки вместе с секретами в репозиторий.

## 2. Проверить существующий cloud до записи

```powershell
npx tgcloud fetch
npx tgcloud --no-pager status
npx tgcloud --no-pager diff
npx tgcloud webhook
```

`fetch` обновляет локальный снимок облака и сохраняет рабочие файлы. `status` и `diff` сравнивают проект с этим снимком; сами работают offline. Сохраните план изменений без секретов.

**Если в облаке уже есть другая программа, неизвестные модули или данные, остановитесь до `push` и согласуйте их сохранение.** Полный `push` делает набор модулей облака равным локальному: отсутствующие локально cloud-модули будут удалены. Не используйте `pull`/`reset` как способ автоматически разрешить расхождение с этой веткой. При конфликте deploy другого разработчика выполните свежий `fetch`, снова изучите `status/diff` и подготовьте согласованный набор файлов. `push --force` запрещён этим checklist.

Первая схема Chipper добавляет `chipper_players(telegram_id, revision, state_json)`. В ней нет удалений таблиц, внешних ключей или зависимости от SQLite JSON1. Существующие таблицы других приложений нельзя удалять или помечать deprecated ради установки игры.

## 3. Собрать production и опубликовать код

Следующие команды предназначены для PowerShell. Mock доступен только в dev; дополнительная проверка анализирует итоговый production bundle. Перед deploy должна существовать новая сборка `dist`, а все проверки обязаны завершиться успешно.

```powershell
$env:VITE_DEV_MOCK = "false"
npm run check
npx tgcloud --no-pager status
npx tgcloud --no-pager diff
npx tgcloud push
```

`npm run check` запускает typecheck, серверную статическую проверку, lint, тесты, production build, проверку отсутствия dev-кода в bundle и проверку секретов. Доступный UI smoke можно отдельно выполнить `npm run test:ui`; он проверяет dev-сценарии и не заменяет приёмку в Telegram. После последней смены исходников/конфигурации повторите `npm run check`.

`push` публикует JavaScript и уже собранный `dist` одной пачкой; базу не мигрирует. Запишите **точный URL из успешного вывода**, SHA и время деплоя. Ошибка `push` или строка с предполагаемым доменом не подтверждают публикацию. Не открывайте релиз тестировщикам до завершения миграции.

## 4. Применить только безопасную миграцию

```powershell
npx tgcloud migrate --dry-run
npx tgcloud migrate --safe
npx tgcloud migrate --dry-run
npx tgcloud webhook
```

Первый dry-run должен показывать ожидаемую новую таблицу/безопасные добавления. `--safe` применяет только safe changes и пропускает warning/manual changes; поэтому его exit code сам по себе не означает готовую схему. Последний dry-run должен подтвердить отсутствие необходимых неприменённых изменений. Если остаются warning/manual изменения или удаление/смена типа существующих столбцов, не запускайте их автоматически: выясните причину и подготовьте отдельный проверенный план.

Не используйте `migrate --yes`, destructive migrations, прямые `DROP/DELETE`, изменение часов/баланса боевых игроков или глобальный сброс. Сверьте webhook с ожидаемым `handlers/message`; восстанавливайте чужие настройки только после выяснения причины расхождения.

## 5. Проверить runtime без подмены live-авторизации

После миграции можно безопасно проверить отказ при отсутствующем Telegram ID:

```powershell
npx tgcloud run endpoints/bootstrap '{}' --ctx '{ initData: { user: {} } }'
```

Ожидается игровой envelope `ok:false`, код `UNAUTHORIZED`, без создания профиля. `run` выполняет локальные модули на платформе и принимает административно заданный `--ctx`; **этот тест не доказывает проверку подписи настоящего Telegram initData**.

Положительную проверку `getHome` через `run` допускается делать после настоящего первого входа аккаунта A, подставив его **собственный уже существующий ID** в документированный контекст `{ initData: { user: { id: ... } } }`. Не запускайте `bootstrap` с вымышленным ID, `101`, `1` или чужим Telegram ID в рабочей базе. Дополнительный live proof атомарного CAS проводится только в отдельном staging-боте/базе с согласованными тестовыми идентификаторами; успешные локальные SQLite concurrency tests не обозначаются как live CAS proof.

## 6. Настроить открытие в Telegram

В [@BotFather](https://t.me/BotFather) выберите **@chipperhatcherybot**:

1. Настройте **Main Mini App** через настройки бота / **Configure Mini App → Enable Mini App**, указав точный HTTPS URL из `push`. После этого ссылка [Открыть Chipper](https://t.me/chipperhatcherybot?startapp), используемая обработчиком `/start`, должна открывать игру внутри Telegram.
2. Настройте **Menu Button** через `/setmenubutton` или **Bot Settings → Menu Button**: текст **Играть**, тот же URL.
3. Отправьте `/start` боту с реального аккаунта, проверьте обе кнопки и запуск из профиля бота. Проверьте запуск на Android/iOS, если доступны, и отдельно Desktop/Web.

Настройка Main Mini App и Menu Button описана в [официальной документации Telegram Mini Apps](https://core.telegram.org/bots/webapps#launching-the-main-mini-app). Открытие HTTPS URL обычным браузером должно показывать предложение запустить приложение в Telegram; production не выдаёт ему игровое состояние.

## 7. Приёмка A/B/C и A1/A2

Выполните полную матрицу [ACCEPTANCE_0.1.md](ACCEPTANCE_0.1.md) и заполните [ACCEPTANCE_RESULT_0.1.md](ACCEPTANCE_RESULT_0.1.md) с датой, SHA, URL и устройствами:

- **A/B/C:** три разных реальных Telegram ID проходят собственное первое вылупление. Проверьте независимые имена, баланс, коллекции, сон и отсутствие чужого кэша после смены аккаунта. Повторный вход восстанавливает прежнего питомца. ID птицы A не позволяет B кормить, переименовать или активировать её.
- **A1/A2:** две сессии одного аккаунта одновременно повторяют действия. Стартовый подарок, покупки, вылупление и награды не дублируются; после потери ответа повторяется прежний operationId. IDOR-проверки должны проходить через настоящий авторизованный endpoint, а не через административный CLI ctx.
- Закройте игру во время сна и инкубации, затем вернитесь. Для первого настоящего сна дождитесь 45 минут; обычное яйцо стоит 6 заработанных пёрышек и инкубируется 3 часа. Долгие 20/72-часовые правила уже проверяются автоматическими контролируемыми часами, но это не разрешение изменять production timestamps.
- Проверьте уход, переключение отдыхающих птиц, мини-игру, ограничение валютной награды, ошибки сети, темы и safe area. Реальные сценарии отмечайте `PASS — live` только после выполнения; оставшиеся — `PENDING — user acceptance`/`BLOCKED` с причиной.

Ни dev mock, ни synthetic `--ctx` не являются приёмкой нескольких настоящих аккаунтов. PR остаётся открытым до решения владельца; merge этот checklist не выполняет.

## 8. Откат без потери профилей

До публикации сохраните рабочий SHA/URL. При дефекте остановите расширение альфы и выберите прежний **проверенный, совместимый со schemaVersion 1 релиз Chipper**. В отдельной чистой рабочей копии восстановите его код, заново соберите production, выполните `fetch/status/diff`, затем обычный `push` без force. Это откат кода и статических файлов; **не откатывайте базу удалением `chipper_players` и не очищайте профили/receipts**. Не запускайте миграцию удаления и не применяйте автоматическое приведение схемы к старому коду.

Если это первый релиз и прежней рабочей игры нет, откатывать на документационный `main` нельзя. Временно уберите вход в неисправную игру через настройки Main Mini App/Menu Button и подготовьте исправленную сборку, сохранив базу. Изменения кнопок/URL фиксируйте для восстановления. Точечный сброс тестового профиля возможен лишь отдельным контролируемым действием в staging; в 0.1 нет кнопки глобального reset.
