## Оркестрация

Три реальных субагента одновременно владели разными файлами: server — `tgcloud/**`; art — `components/**` и art.css; screens — App/screens/app.css/i18n. Оркестратор создал scaffold, контракт, адаптер, тесты, CI, интегрировал и повторно проверил результат. Арт-агент дополнительно провёл независимый обзор серверных инвариантов и UI; серверный агент отдельно проверил clock/replay/границы. Окончательный статус определяется воспроизводимыми проверками в отчёте, а не только заявлениями агентов.

## Подтверждённая платформа

`npx tgcloud init --no-git` реально выполнен в существующем Vite-проекте. Сигнатуры взяты из созданного [tgcloud-sdk.md](tgcloud-sdk.md) и [официального Serverless описания](https://blogfork.telegram.org/bots/serverless). Flat endpoints/handlers, относительные .js imports, no npm/Node API в runtime. Raw `db.get` возвращает строку; `db.run` — `{rowsAffected,lastInsertRowid,rows}`, включая RETURNING. Foreign keys отсутствуют. Публикация и миграции — разные команды.

[Telegram Mini Apps](https://core.telegram.org/bots/webapps) и Serverless предоставляют callback `Telegram.WebApp.Serverless.call(name,input,callback)`. Производственный клиент использует его напрямую, без самодельной проверки initDataUnsafe. Контекст `ctx.initData` проверяет платформа до вызова endpoint; это свойство ещё необходимо проверить живым запуском.

## Модель атомарности

Одна таблица `chipper_players`: Telegram ID primary key, nonnegative revision, JSON state. Логические chicks/eggs/care_milestones/reward_claims/operation_receipts/attempts/telemetry находятся в одной строке. INSERT стартового профиля содержит всё стартовое состояние сразу. CAS сохраняет расход и создание яйца, hatch и птицу, выдачу и receipt одним SQLite statement. Если процесс/ответ прерывается после commit, повтор находит receipt. Hatch history дополнительно возвращает тот же chickId при новом operationId.

Каждый receipt связан с нормализованным fingerprint метода и параметров. Повтор того же UUID с другими параметрами отвергается. При32 последовательных конфликтах возвращается retryable ошибка; клиент повторяет прежнюю операцию. Проверки ownership выполняются до записи. Клиентские ownerId/userId/amount/appearance/readyAt отклоняются.

Те же raw SQL проверены на настоящей локальной SQLite с искусственным чередованием запросов. Это подтверждает алгоритм и SQL; реальные транспорт, лимиты runtime и реализация платформенной БД не выдаются за проверенные в Telegram.

## Клиент и восстановление

Снимок production-профиля хранится только в памяти. Signed initData используется как непрозрачная граница идентичности, не как клиентское доказательство. Смена ключа размонтирует старый App; поздний ответ прежнего аккаунта отклоняется. Во время скрытия окно не отображает игровую поверхность, при возврате ключ проверяется перед показом. Pending UUID сохраняется на время того же mounted аккаунта; ошибки повторяются с прежними параметрами.

Отображаемые таймеры используют performance.now от полученного serverNow; баланс/потребности/рост подтверждаются сервером. Фоновое обновление сверяет остальные сессии и завершение таймеров. Во время мини-игры background refresh не занимает блокировку finish. Если игру закрыть полностью посреди раунда, её можно начать снова; попытка имеет TTL и не даёт награду без завершения.

DevMock — compile-time DEV-only dynamic import, явный баннер, синтетический профиль101/localStorage. Production build проверяется на отсутствие dev-backend и тестовых identities. Настройки устройства отдельно от игрового профиля.

## Известные пределы

1. Живые Telegram A/B/C/A1/A2, Android/iOS/Web, платформенные миграции и CAS требуют доступа и ручной приёмки. Актуальный deploy-статус только в ACCEPTANCE_RESULT.
2. Бессрочные receipts/history/attempts увеличивают агрегат; вся строка читается/переписывается. Для закрытой альфы приемлемо, для широкого запуска нужны измерения лимитов и replay-safe компактация. Нельзя просто удалить старые receipts.
3. Косметическая случайность серверная; runtime crypto используется при наличии, иначе Math.random. Криптографическая гарантия runtime не заявляется.
4. Мини-игра защищена от прямой выдачи/раннего finish/чужой попытки/replay, но клиентский счёт можно автоматизировать. Денег и рейтинга нет.
5. Никаких production time travel, выдачи тестовых пёрышек или массового reset. Долгие таймеры ускоряются исключительно в tests.
6. Формальная политика приватности/удаления данных — шаг перед открытым релизом. Alpha UI объясняет использование ID; лишние персональные данные не запрашиваются.

Скриншоты в [qa/](qa/) показывают настоящие отрендеренные локальные сборки и оригинальный SVG-каталог, **не живой Telegram**.
